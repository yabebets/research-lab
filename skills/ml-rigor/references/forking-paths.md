# 分岐の庭 — 見抜き方と予防

社会科学の p-hacking の分類（AERS の `p-hacking-skills` が扱う「分岐の庭」「仕様探索」「物語の洗浄」）を、ML の実験に置き換えた対応表。各項目は「どこで起きるか → 痕跡の探し方 → 予防」の順。

| # | 分かれ道 | 痕跡の探し方（runs/ と git で確かめる） | 予防 |
|---|---|---|---|
| 1 | seed 選び | `runs/` の seed の数と、表に出ている seed の数が一致するか。`status: done` の実行がすべて集計に入っているか | 事前登録で seed 数を固定。集計スクリプトは `runs/` を全部読む作りにする（手で選ばない） |
| 2 | チェックポイント選び | `metrics.json` に `split: test` が学習の途中で何度も出ていないか | 途中評価は val のみ。test は最終チェックポイントで 1 回 |
| 3 | テストでの調整 | test の評価回数（`rl status` が数える）が事前登録の上限を超えていないか。プロンプトや閾値の変更履歴（git log）と test 評価の時刻の前後関係 | test 評価の回数に上限。超えるなら止まって人に確認 |
| 4 | ベースラインの手抜き | ベースラインの設定ファイルの数と、提案手法の探索の数。報告値を引用したなら設定（データの版・解像度・評価スクリプト）が同じか | 調整予算を揃える。揃えられない場合は本文で明記 |
| 5 | ベンチマークの取捨 | 計画にあったが表にないデータセット・課題 | 計画の課題はすべて報告（負けも付録に） |
| 6 | 指標の乗り換え | 主張の根拠が事前登録の主指標か | 主指標は 1 つに固定 |
| 7 | 汚染・漏洩 | LLM：テスト問題の n-gram の重なり、公開日と学習データのカットオフ。CV：train と test の画像の重複（知覚ハッシュ）。前処理：正規化の統計量の出どころ | 汚染チェックを S3 の最初にやる。結果を付録に |
| 8 | 評価方法の違い | 提案手法とベースラインで評価コードが別になっていないか | 同じ評価関数を通す。公式の評価スクリプトを優先 |
| 9 | 失敗した実行の除外 | `status: failed` や NaN の実行の扱い | 除外基準は事前に。件数と理由を報告 |
| 10 | 最良 N から選ぶ | 生成・試行の回数が条件間で同じか | 「pass@k」「best-of-N」は全手法で同じ k・N |
| 11 | sim だけの主張 | `claims.yaml` の `eval_type` | sim と実機を表で分ける |
| 12 | 実機の試行の選び方 | 試行のログ（動画のファイル数と試行数）が一致するか。順番が「A を全部→B を全部」になっていないか | 交互またはランダムな順番。全試行を録画。成功の判定は事前に文で決める |
| 13 | 範囲の誇張 | 「robust」「generalizes」の根拠になるシーン・物体・環境の数 | 数を本文に書く。少ないなら「予備的」 |
| 14 | 計算量の不公平 | パラメータ数・学習ステップ・データ量・推論時の計算 | 計算量を揃えた比較を 1 つは入れる |

## 物語の洗浄（書く段階で起きること）

- **後づけの仮説**：結果を見てから仮説を書き換えていないか → `plan.md` の事前登録と比べる。後から見つけたことは「探索的な発見」と書く
- **限定の削除**：分析では「この条件では」と付いていた限定が、Abstract で消えていないか → ARIS `paper-claim-audit` と `claims.yaml` の `strength` で照合
- **負の結果の省略**：効かなかったアブレーションを書いていないか → 付録に入れる
