# ml-rigor — 実験の厳密さ

AERS（Auto-Empirical-Research-Skills）の「p-hacking を検出・予防するスキル群」と「機械で採点する評価ハーネス」の考え方を、ML・ロボティクスの実験向けに書き直したもの（AERS の文章は使っていない）。ARIS の `shared-references/experiment-integrity.md`（偽の正解データ、指標の正規化の不正、存在しない結果、範囲の誇張の禁止）も前提として守る。

## いつ使うか

| 段階 | やること |
|---|---|
| S2 計画 | **事前登録**を `plan.md` に書く（下のテンプレート）。G2 で人が承認したら `research.yaml` の `protocol` に写して固定する |
| S3 実験 | 実行ごとに `runs/<id>/` に seed・設定・split を残す。テストセットの評価回数を数える |
| S4 分析 | 統計は必ず `scripts/rl_stats.py` で計算する（暗算しない）。**分岐の庭のチェック**を全項目やり、結果を `notes/rigor-audit.md` に表で残す |
| G3 前 | チェックで FAIL が残っている主張は、`strength: qualified` か `exploratory` に下げる |

## 事前登録のテンプレート（plan.md に書く）

```markdown
## 事前登録（G2 で承認後は変更しない）
- 仮説: H1 …（反証できる形で。何がどれだけ変われば支持／不支持か）
- 主指標: …（1 つ。副指標は列挙するが、主張の根拠は主指標）
- データの分割: train / val / test の出どころ。test は最終評価でだけ使い、回数は ≤ N 回
- seed 数: ≥ 5（予算が厳しければ 3。3 未満は「予備的」と明記）
- ベースライン: 名前・出典・再現 or 報告値の引用。**調整予算（試す設定の数・GPU 時間）を提案手法と同じにする**
- アブレーション: 何を外して何を確かめるか
- 統計: 比較の方法（ペアのブートストラップ／並べ替え検定、RL は IQM、実機は Wilson と Fisher）、多重比較の補正（Holm）
- 実機評価（あれば）: 条件ごとの試行数（`rl_stats.py trials` で決める）、物体・初期配置の決め方、条件の実施順（交互・ランダム）、成功の判定基準（事前に文で書く）、評価者が条件を知らないか
- 打ち切り: どうなったら仮説を捨てる・方向を変えるか
- 再現性: 評価の環境を固めたコンテナのイメージ（指紋を記録）、本番を回す計算機、別の計算機で回し直す抜き取り、判定・評価の上限は回数で（秒にしない）、公開するコードとデータの置き場（references/reproducibility.md）
```

## 分岐の庭（結果を良く見せてしまう分かれ道）のチェック

S4 で全項目を確認し、`notes/rigor-audit.md` に `項目 | 判定（PASS / FAIL / N/A） | 根拠（run_id やファイル）` の表で残す。詳しい説明と見抜き方は [references/forking-paths.md](references/forking-paths.md)。

1. **seed 選び**：良かった seed だけを報告していないか。全 seed を報告しているか
2. **チェックポイント選び**：テストセットの成績で最良のステップを選んでいないか（選ぶのは val で）
3. **テストセットでの調整**：ハイパーパラメータ・プロンプト・閾値をテストで決めていないか。test の評価回数は事前登録の範囲か
4. **ベースラインの手抜き**：提案手法だけ調整していないか。ベースラインの数値の出どころ（再現 or 引用）と設定の違いを書いているか
5. **ベンチマークの取捨**：負けた課題・データセットを黙って外していないか
6. **指標の乗り換え**：主指標で負けて、副指標を主張の根拠にしていないか
7. **汚染・漏洩**：テストデータが学習データや事前学習のコーパスに入っていないか（LLM は特に。n-gram の重なり、公開日、Canary）。前処理の統計量を test から計算していないか
8. **評価方法の違い**：few-shot の書式、解析の仕方、解像度、後処理がベースラインと揃っているか。公式の評価スクリプトを使っているか
9. **失敗した実行の除外**：落ちた・発散した実行を黙って外していないか（外すなら基準を事前に決め、件数を報告）
10. **最良の N 回から選ぶ**：「N 回生成して最良」をベースラインにも同じ条件で適用しているか
11. **シミュレーションだけの主張**：sim の結果を実機の主張にしていないか（`eval_type: sim_only`）
12. **実機の試行の選び方**：うまくいった試行だけ動画・数に入れていないか。リセット・初期配置は事前に決めた方法か。条件の順番は交互・ランダムか
13. **範囲の誇張**：「robust」「extensive」「across settings」に見合う数か（N 個のシーン・seed・設定を明記）
14. **計算量の公平さ**：提案手法の追加の計算（パラメータ数・FLOPs・GPU 時間・データ量）を報告し、同じ計算量のベースラインと比べているか

15. **再現できない環境での本番**：本番の評価を、固定していない環境（個人の計算機の今の状態、版を固定していない依存、秒で切る上限）で回していないか。イメージの指紋・計算機・OS を記録し、別の計算機で一部を回し直したか（[references/reproducibility.md](references/reproducibility.md)）

## 再現性と公開

主な会議・分野の慣行（NeurIPS の評価とデータの部門、再現性のチェックリスト、ACM の成果物の評価、ロボティクスのベンチマークの Docker のイメージ）に合わせる。要点は「環境をコンテナのイメージに固めて指紋を残す」「本番は 1 台で回して計算機を記録する」「別の計算機で一部を回し直して食い違いを報告する」「計算機をまたいだビット単位の一致は前提にせず、統計で示す」「コードとデータは投稿の時点で実行できる形で出す」。チェックリストは [references/reproducibility.md](references/reproducibility.md)。G2 で plan.md に書き、G3・G4 の前に確かめる。

## 統計の決まりごと

すべて `python3 ~/research-lab/skills/ml-rigor/scripts/rl_stats.py <サブコマンド>` で計算する（`--json` で機械が読める出力）。

| 場面 | やり方 | コマンド |
|---|---|---|
| 1 条件の性能 | 平均 ± 標準偏差と 95% CI（seed 間）。n<5 は予備的 | `ci v1 v2 ...` |
| 2 条件の比較（同じ seed・同じ課題で対） | 差の CI と、符号反転の並べ替え検定。**seed が 5 個だと最小の p は 0.0625**（有意と言えない）ので、seed を増やすか、課題 × seed で対を作る | `paired --a ... --b ...` |
| RL・多課題 | 平均でなく IQM と層別ブートストラップの CI（rliable と同じ考え方） | `iqm scores.json` |
| 実機・成功率 | Wilson の信頼区間。n=20 だと ±20pt 近く揺れる | `wilson k n` |
| 実機・2 条件の成功率の差 | Fisher の正確検定 | `twoprop k1 n1 k2 n2` |
| 何回試行すればいいか | 検出したい差から逆算（目安の下限） | `trials p1 p2` |
| 複数の比較 | Holm 補正 | `holm p1 p2 ...` |
| 注釈者 2 人の一致（正解のラベル） | Cohen の κ と項目のブートストラップの CI。順序のある値は 2 次の重みの κ。κ < 0.6 の項目は決め方を直す | `kappa --a ... --b ...` か `kappa pairs.json [--weights quadratic --categories 0 1 2+]` |
| 注釈者 3 人以上（全項目を同じ人数） | Fleiss の κ | `fleiss ratings.json` |
| 欠けのある一致・順序や間隔の尺度 | Krippendorff の α（nominal / ordinal / interval） | `alpha data.json --level ordinal` |

書き方の決まり
- 表には平均だけでなく、ばらつき（± std か CI）と n を必ず書く。差が CI に収まるなら「同等」と書き、「上回る」と書かない。
- p 値は補助。主張の強さは効果の大きさと CI で決める。
- ロボットの実機評価は、条件ごとの試行数・成功の判定基準・失敗の内訳（把持失敗・衝突・タイムアウトなど）を表にする。
- 注釈の一致は項目ごとに κ（または α）・CI・n を表にする。全件が同じ値で κ が定義できない項目は一致率だけを書き、「一致した」と書かない。
