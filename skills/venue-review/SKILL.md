# venue-review — 学会別の査読シミュレーション

## 大事な前提

- **学会の決まり（ページ数、必須の節、チェックリスト、LLM の使用の申告、匿名化）は毎年変わる。** 査読の前に、その年の Call for Papers と著者ガイドを WebFetch で読み、`notes/venue-<学会>-<年>.md` に要点を写す。下の表は観点の目安で、最新の規則の代わりにはならない。
- 査読役は **別モデル**（ARIS の Codex 査読役。プロジェクト内なら `/research-review` や `/auto-review-loop`）を基本にする。自分で書いた原稿を自分だけで査読して合格にしない。
- 査読の結果は `notes/reviews/<日付>-<学会>.md` に残し、点数の推移を追う。

## 学会ごとの観点（目安）

| 分野 | 学会 | 必須・重視されること（毎年確認） |
|---|---|---|
| ML | NeurIPS | 論文チェックリスト（未記入は却下の対象）、主張と証拠の対応、限界の記述、再現性（コード・ハイパーパラメータ・計算資源）、統計的な有意性の報告 |
| ML | ICLR | OpenReview で公開の議論になる。再現性・倫理の声明、LLM の使用の申告。査読者との往復を前提に、追加実験の余力を残す |
| ML | ICML | 影響の声明（Impact Statement）、理論の主張なら仮定と証明の完全さ |
| CV | CVPR・ICCV・ECCV | 標準ベンチマークでの比較表、定性的な図（成功と失敗）、アブレーション、補足資料（動画）。匿名性に厳しい |
| NLP | ACL・EMNLP・NAACL（ARR） | Responsible NLP チェックリスト、**Limitations の節が必須**、データ・モデルのライセンスと倫理、評価の汚染への配慮 |
| ロボティクス | CoRL | 実機の実験の重み、**Limitations の節**、動画、学習の手法としての新しさ |
| ロボティクス | RSS | 新しさと厳密さの両方、システムとしての説得力 |
| ロボティクス | ICRA・IROS・RA-L | IEEE の書式、動画の添付、実機での検証。RA-L は ICRA・IROS での発表を選べる |
| システム | MLSys・OSDI・SOSP | 実システムでの評価、Artifact Evaluation、比較の公平さ（同じハード・同じ条件） |

## 査読シミュレーションの手順

1. **学会の評価フォームに合わせる**：その年の評価項目（例：Soundness / Presentation / Contribution / Overall、ARR なら Soundness / Excitement / Overall Assessment）を `notes/venue-*.md` から取る。
2. **査読者を 3 人と AC にする**：分野の専門家、手法の厳密さの担当（`ml-rigor` の観点）、隣の分野の読み手（わかりやすさ）。ロボティクスなら 1 人は実機の経験者の視点。
3. **各査読者に要求する形式**：
   - 要約（著者の主張を 3 行で）
   - 強み 3 つ、弱み 3〜5 つ。**弱みには原稿の該当箇所（節・表・図・行）を必ず付ける**。根拠を示せない弱みは書かない
   - 追加で必要な実験（費用の目安つき）
   - 点数と確信度
4. **AC のまとめ**：採否の見込み、決め手になる弱点、直す順番（効果 ÷ 手間）。
5. **直す → もう一度査読**：ARIS `auto-review-loop` に任せてよい（上限回数を決める）。原稿を直したら、前回の弱点がそれぞれ解消したかを表で確認する。

## 査読役が甘くならないための決まり

- 著者側（このエージェント）の反論で弱点を取り下げるのは、**原稿の具体的な箇所か新しい実験の結果で反証できたときだけ**。言い分を聞いて取り下げない。
- 点数は、直した内容が原稿に入ってから付け直す（「直す予定」で上げない）。
- 毎回、査読役には新しい文脈（前回の自分の評価を見せずに）で 1 回は読ませ、前回の評価に引きずられていないかを見る。

## G4（投稿の判断）に出すもの

- 想定される点数の範囲と、残った弱点（直せるもの・直せないもの）
- 投稿先の候補の比較（締切・合いそうな度合い・リスク）
- 必須チェックリストの記入状況、匿名化の確認、補足資料の準備状況
